# Agent Team Lead

[English](README.md) | [简体中文](README.zh-CN.md) | [日本語](README.ja.md)

**一人のリーダーと複数の開発エージェントで、検証済みの成果物まで仕事を進める。**

Agent Team Lead は、異なるハーネスを使う開発エージェントのチームを管理するスキルと実行ツールの構想です。調整エージェントが計画、委任、進捗確認、復旧、受け入れ検証を担当します。実行エージェントは実装、テスト、レビュー指摘の修正を行います。利用者は方向性を決め、進捗を確認し、自分の権限が必要な事項を判断します。

検証済みの成果、正確な進捗、利用枠の確保を重視し、利用者の注意と調整の負担を減らします。成果・責任・権限の境界を定め、エージェントの判断を尊重し、既存の品質チェックと標準の自動化機能を優先します。

## プロジェクトの状態

**現在は設計文書のみです。インストール可能なスキル、実行ツール、アダプター、プラグインはまだありません。**

フロントエンド移行の並行実行と Webhook サービス開発という二つの実案件での実験は終了しました。証拠の確認結果を[初版の設計レビュー案](docs/v0-design.md)（中国語、承認待ち）にまとめています。互換性や信頼性を保証するものではありません。実装はまだ開始しておらず、初版の範囲の承認を待っています。

## 役割

| 役割 | 責任 |
| --- | --- |
| 利用者／プロジェクト責任者 | 目標と制約を設定し、進捗を確認し、委任した権限を超える事項を判断する。 |
| 調整エージェント／リーダー | タスク全体に責任を持ち、実行担当の選択、依存関係の管理、障害対応、受け入れ検証、後片付けを進める。 |
| 実行エージェント | 範囲内の実装とチェック、設定された独立レビューと修正を行い、証拠と引き継ぎ記録を残す。 |
| 決定的な実行ツール | プロセスとイベントの追跡、記録の検証、通知の重複排除、健全性確認、許可済みのライフサイクル操作を行う。 |

進行に対する責任はリーダーにあります。実行担当から結果が返ることは引き継ぎであり、自動的な受け入れ完了ではありません。

## 設計原則

1. **完了まで管理する。** 一貫した目標を委任し、利用者が何度も催促しなくても検証と後片付けまで進めます。リーダーは判断と調整を行い、個々のコマンドを細かく指示しません。
2. **判断と定型処理を分ける。** スクリプトは通常の確認と状態遷移を、モデルは計画、診断、レビュー、意思決定を担当します。通常の監視でモデルを繰り返し呼び出しません。
3. **プロジェクトの状態を永続化する。** 範囲、決定、実行識別子、候補リビジョン、証拠、障害、次の操作をプロジェクトとともに保存します。会話履歴を唯一の復旧手段にしません。
4. **進捗を見えるようにする。** ツール本来の状態表示とログを優先し、観測できた操作と最終更新からの時間を示します。完了率を推測したり、プロセスの活動を業務上の進捗と混同したりしません。別の監視アプリは必須にしません。
5. **慎重に復旧する。** 出力がないだけで失敗とは判断しません。プロセス終了と監視障害を検出し、状態を保存し、回数を制限して通知を再試行します。安全であれば元のタスクを再開し、副作用のある処理を無条件に再実行しません。
6. **委任された権限内で動く。** ホストが対応している範囲で必要な操作を事前承認し、本当の例外だけを利用者に確認します。異なるハーネス間で権限を共有できるとは仮定せず、シェル全体を無制限に許可しません。
7. **独立して検証する。** 成果物とレビュー証拠をタスク、実行、候補リビジョンに結び付けます。実際の変更と関連する結果を確認し、終了コード、担当者の報告、レビューラベルだけで完了とは判断しません。
8. **選択的に並列化する。** 作業ツリーとタスク成果物を分離し、必要に応じて共有アカウント、変更可能なテスト資源、統合を直列化します。受け入れ検証が滞る場合は並行数を制限します。
9. **利用者を定型的な調整から解放する。** 重要な節目、対処が必要な障害、最終結果を報告します。通常の進捗は標準画面や決定的な通知で伝え、更新のたびにモデルで要約しません。
10. **中核を特定ツールから独立させる。** 役割を製品名に結び付けません。信頼できる標準機能を優先し、必要な場合は明示的なスクリプトで補い、能力の不足を記録します。

## 想定アーキテクチャ

| 層 | 想定する内容 |
| --- | --- |
| 汎用スキル | リーダーの手順、委任契約、復旧判断、受け入れ検証、報告ルール。 |
| 共通実行ツール | プロセスとイベント処理、健全性確認、成果物記録の検証、通知の制限付き再試行、後片付け。 |
| ハーネス別アダプター | 各ツールの対応インターフェースによる起動、再開、状態確認、メッセージ送信、中断、能力確認。 |
| プロジェクト設定 | 要件の入口、検証コマンド、レビュー連携、環境情報への参照、権限境界、共有資源のルール。 |

Claude Code、Codex、Antigravity、OpenCode、DeepSeek Harness は連携候補であり、実装済みのアダプターではありません。Codex 標準のサブエージェントも実行方法の候補です。どちらの役割も特定のベンダーに依存しません。

ハーネス間での同等の能力、無制限の無人実行、すべての関連プロセスが停止した後の継続動作は保証しません。イベントには処理確認が必要です。調整セッションが通知を受信できない場合の代替手段も必要です。

## 配布計画

一つのソースリポジトリから `npx skills` でインストールできる Agent Skills パッケージと、Codex／Claude Code 用プラグインを提供する計画です。これらのインストール方法は**未実装**です。実行依存関係、ホストの権限、バックグラウンドサービス、アダプターの互換性は別途文書化します。スキルをインストールしても、自動的にそれらが設定されるわけではありません。

## 実装前に行うこと

- 初版の目標、ユーザー体験、責任、範囲、受け入れシナリオを確認します。非公開の振り返り資料は Git に含めません。
- ホストとプロジェクトの既存機能を優先します。[delegate-skills](https://github.com/amElnagdy/delegate-skills)、[acpx](https://github.com/openclaw/acpx)、[CLI Agent Orchestrator](https://github.com/awslabs/cli-agent-orchestrator) は参考候補であり、初版の外部依存やソースコードの再利用は選定していません。
- 書面の設計承認後に実装計画を作成し、実行側の自動承認と復旧を含む具体的な実行経路を選定します。計画の承認後に実装します。
- 人による介入、コンテキスト復元の負担、調整モデルの呼び出し回数、検証済み成果を測定します。測定前に削減率を主張しません。
