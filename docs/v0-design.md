# Agent Team Lead 首版设计评审稿

状态：讨论共识已整理，本文待 Boss 评审；尚未制定新实施计划或开始实现。本文替代此前以固定运行路径和详细状态机为中心的提案，沿用项目文档位置。两项实验的脱敏依据独立保存在 [证据摘要](evidence-summary.md)，原始材料仅本地保留。

## 1. 目标与成功标准

Boss 在一个 Agent 会话中交代开发目标，由当前 Agent 担任 Leader，组织执行 Agent，持续推进至可信交付。Boss 主要关注交付成果、进度和成本，不负责日常路由、审批或上下文搬运。

质量是硬约束。在满足质量的前提下，优先避免稀缺的 Leader 额度被无效工作耗尽，并减少 Boss 的注意力消耗，再优化执行时间。合理增加执行时间可以接受，但交付预期发生明显偏差时必须及时说明，不能静默拖延。

成功应能从实际任务中观察到：Boss 确认开工后无需持续催促；例行审批不反复唤醒 Leader；交付有真实证据；换 Agent 接手时无需 Boss 重述背景。记录 Boss 介入原因、Leader 被唤醒的原因、实际交付耗时与估计偏差，用于判断机制是否有效，不预设节省比例。

## 2. 开发原则

- **围绕成果组织协作。** 明确交付标准、责任和授权边界，让 Agent 自主规划、选择工具及调整路径。Skill 不逐条指挥实现命令。
- **少约束，保留必要底线。** 不越权、不虚报、不破坏无关工作；关键状态可恢复，交付证据可核对。需要硬限制时交给合适的权限或确定性机制，不能只依赖提示词。
- **优先复用。** 接入项目已有 Harness 文档、测试、评审和工具原生能力；缺什么补什么，不叠加一套完整开发体系。
- **机械工作不用模型。** 状态采集、持久化、去重、通知重试和可计算校验尽量使用原生能力或可复用脚本；脚本不代替业务判断。
- **按任务裁剪。** 开工确认、必要决策、验收是协作约定；内部阶段、记录格式、采样间隔和返修次数不统一强制。根据任务与证据选择足够的流程。

## 3. Boss 的交互流程

### 3.1 交代目标与开工确认

Boss 在支持该 Skill 的会话中提出目标。Leader 先读取项目约定、任务记录和实际状态，只追问会改变目标、质量、成本或授权边界的关键歧义，然后提供简短的 **开工简报（Kickoff Brief）**：

| 内容 | Boss 需要判断的事项 |
| --- | --- |
| 成果与范围 | 最终得到什么，本次边界是什么 |
| 执行安排 | 选择哪些执行 Agent、理由、主要阶段及依赖 |
| 时间与成本预期 | Leader 估计的交付时间或区间、主要不确定性、已知额度限制与消耗风险 |
| 验收办法 | 项目已有门禁、缺口和本次补充办法 |
| 两层授权与风险 | Leader 可自主决定什么，执行端需要哪些权限，哪些事项仍需 Boss 决策 |

Boss 可以指定执行 Agent；未指定时 Leader 按任务适配、能力、成本、可用性及自动审批能力选择，给出结果与理由。Leader 模型由当前会话决定，不要求使用前沿模型。

开工简报是启动执行的统一确认点。Boss 确认后，Leader 在约定范围内持续推进，不重复请求例行批准。后续任务实质扩围、需要新授权或无法可靠继续时才提出决策；无需因普通计划调整重走完整开工流程。

### 3.2 执行、进度与例外

执行 Agent 接受完整目标及项目质量要求，自行实现、测试、评审和返修。Leader 负责组织规划、依赖、必要协调、异常判断和验收；任务内部动作由执行端自主安排。

Boss 主动询问时，Leader 核对最新状态，简短回答当前成果、活动或阻塞、下一步和交付预期；过期记录明确标注，不把进程存活当业务进展。普通状态由机械采集落盘，不生成定时模型汇报，也不默认发系统横幅。

主动汇报发生在：Leader 实际介入的重要阶段交接、交付预期或额度可用性明显变化、需要 Boss 决策、最终交付。Leader 介入时顺带汇报阶段变化；执行端内部的正常切换不为播报单独唤醒 Leader。

局部阻塞时，只暂停受影响的部分，继续推进不受影响的工作。向 Boss 请求决策时说明问题、证据、对成果/时间/成本的影响、选项及推荐理由，并说明哪些工作仍继续。

### 3.3 交付

默认给 Boss 四项：**成果入口、验证结果、遗留问题、成本摘要**。成本摘要说明实际耗时与原估计的差异、已知额度受限及影响；详细日志、Token 和过程证据按需查看。未完成的检查、人工业务验收或清理不能隐藏在“完成”中。

## 4. 两层授权与执行端自审批

Boss 授予 Leader 组织、协调和必要操作的范围；Leader 据此为执行 Agent 配置足够完成任务的权限与工具。业务授权与 Harness 的实际许可分别核对，不能假定两者等价。

优先使用执行工具自身的自动审批或自动审查能力，在既定边界内由执行端处理常规权限请求。开工简报说明拟用模式、可用性及限制；Boss 确认后启动时再核对实际生效情况，仅有配置声明不足以证明运行已采用。首版不自建审批模型或审批服务，不把宽泛 Shell 放行当作自动审查。

权限拒绝先由执行 Agent 使用已允许的等价入口；无法在既有授权内解决时才通知 Leader。Leader 可按已有授权处理局部许可配置；超出授权再交 Boss。自动审查拒绝不能被简单解释成应绕过安全机制；无人可审批的拒绝也不能伪称为等待点击的窗口。

执行端自审批是否真正减少 Leader 介入，是执行路径验收的一部分。不能选完低费率模型后，把大量常规审批转嫁给昂贵的 Leader。

## 5. 质量与真实性

项目 Harness 文档与脚本承担第一道门禁。缺少足够规范或质量脚本时，Leader 在开工简报中提出缺口及本次最低验收办法，由 Boss 一并确认；不要求先为项目建设完整 Harness。

执行 Agent 完成项目要求的测试、独立评审和返修，留下可定位的原始结果与对应版本。Leader 自行判断核验深度，重点防止虚报、漏报、把未执行说成通过、引用旧候选或不完整评审。根据疑点读取真实改动与结果，必要时定向复验，不机械重跑所有检查。

进程退出、退出码为零、完成标签和脚本门禁通过，均不足以单独证明交付成立。版本或内容变化后，核对原证据是否仍有效。返修不为追求“零评论”无限循环；是否继续取决于实际缺陷、覆盖缺口及投入，明显不收敛时由 Leader 判断，必要时汇报 Boss。

## 6. 可恢复的任务现场

Leader 和执行 Agent 都持续维护项目任务记录，优先扩展已有文档；同一事实明确维护方，互相引用，不复制出多份矛盾的状态。Leader 维护总体目标、开工确认、授权、安排、决策和下一步；执行端维护本任务进展、改动、验证、评审和阻塞。机械运行数据由脚本采集。

只要求保留接续必需的信息，不固定文档数量或 JSON 文件矩阵：

- 目标、范围、验收约定、授权来源及关键决定。
- 工作目录/分支、执行工具、会话与本次运行身份、候选版本。
- 已完成与未完成事项、证据位置及其适用版本。
- 当前阻塞、负责人、下一步，以及尚未确认结果的外部操作。

关键动作前记录意图，结果产生后及时记录；文档和运行记录放在不会随临时工作树清理消失的位置，写入需避免半文件或并发覆盖。机器路径、原始日志、会话标识和凭据不得因默认归档进入公共 Git；可提交内容与本地运行态分开。

额度耗尽时，执行 Agent 可在既定范围内继续；遇到必须由 Leader 决策的问题再暂停受影响部分，最终验收等待 Leader。Leader 无法可靠解决问题时汇报并保存现场，由 Boss 决定继续、切换模型或交给更高级的 Agent；不自动后台咨询强模型。

新 Agent 从 Boss 指定的项目/任务入口恢复，先读记录，再核对实际代码、进程、产物和未处理事件。保留有效执行会话，不重复派发；无法恢复原会话时，以同一任务记录显式建立接续运行。崩溃前最后一次写入之后的操作可能结果未知，需先对账，不能承诺零信息损失或盲目重做外部写入。

## 7. 成本与交付预期

Boss 主要关心订阅额度够不够用，以及交付是否超出时间预期。Leader 避免在常规审批、高频巡检、重复阅读和重复验证上浪费额度，不建设精细预算系统。

能获取时使用工具原生的剩余额度、重置时间和使用统计；获取不到就标记未知或部分可见，不用 Token 猜额度百分比，也不宣称自动预测剩余额度能完成多少工作。额度明确受限时记录其对进度的影响。执行 Agent 的时间与 Token、Leader Token 可作为后台诊断数据，区分来源和统计范围，不为统计专门消耗模型。

Leader 根据任务、依赖及已知条件估计交付时间，并在发现明显偏差时主动更新原因、影响和下一步。记录任务总历时；执行时间、等待时间及多 Agent 耗时按工具可得数据区分，不把并行耗时简单当总工期。

## 8. 首版边界与职责分层

首版提供精简的 Leader Skill、必要的可复用机械辅助及一条实际跑通的执行路径。以一个项目、一个 Boss 目标、一个执行 Agent 完成全链路为发布验收范围；可组合多个执行者是长期方向，不在首版建设并行调度平台。

| 归属 | 首版责任 |
| --- | --- |
| Skill | 开工简报、组织委派、两层授权、进度与例外沟通、真实性核验、交接与交付约定 |
| 项目 Harness | 项目标准、验证命令、独立评审及质量门禁；缺口按任务补齐 |
| Harness/宿主原生能力 | 模型执行、自动审批、会话检查与恢复、可用的事件入口、使用统计 |
| 可复用脚本 | 原生能力缺失时补运行身份、持久记录、低成本监控、可靠事件处理、必要校验和资源清理 |

脚本按缺口增加，不默认重建 runner、通用适配器或整套任务平台。事件观察、发送和处理确认分开；未处理异常不能被普通快照覆盖，重复投递不能触发重复执行。通知失败须保留问题并暴露降级状态，不能把入队成功等同处理完成。

首版工具组合在后续实施计划中依据能力核对确定，选择条件是：已有实验依据、可重现启动、执行端自审批可用、运行状态可查、可持久接续、交付证据可核验，以及 Leader 能接收必要事件。不绑定某个模型品牌；也不承诺所有可安装 Skill 的宿主都已支持全套闭环。缺少推送能力的宿主必须在开工简报说明需要手动接续，不能称为全自动路径。

原提案固定的 Codex→Claude 打印模式不再是已选定方案：其启动可还原，但无法仅凭这一点证明审批成本满足新目标。原生后台模式有实际完成任务的依据，但完整首发参数和部分权限记录仍需核实。实施计划必须选定并说明一条具体路径及能力缺口，再交 Boss 确认，不能以模型聪明替代工具验证。

首版不做模型自动升级/路由、完整成本计费系统、多 Harness 全功能适配、监控 App、复杂 DAG、统一业务质量引擎。数据与状态应支持死机后接续，不承诺休眠/关机期间持续执行、自动开机恢复或通知严格及时。清理只触及本任务资源，集成、push、发布和部署按具体授权执行。

## 9. 设计验收场景

以下为后续实施的可观察标准，尚未实现。机械故障用隔离环境验证，选定路径还须真实演练；不因现有实验的单项证据而宣称组合已跑通。

| 场景 | 预期体验与证据 |
| --- | --- |
| 开工与正常交付 | Leader 给出完整简报及执行者选择理由；确认前不派发；确认后自主完成项目门禁、评审返修、验收和授权收尾，交付四项摘要 |
| 执行端权限 | 范围内常规操作由执行端自审批；拒绝时先找已授权替代，不逐条通知 Leader；真正越界停下请求决定，自动模式实际生效可核对 |
| 局部阻塞 | 汇报问题及影响，继续无依赖工作；请求决策有选项和推荐；阻塞不被新进展覆盖 |
| 进程退出或长时间无输出 | 分开识别进程退出、工具失败、安静执行和等待；不凭无输出杀进程；核实现场后接续，不重复派发或重做未知副作用 |
| Leader 额度耗尽 | 执行端继续已授权工作，需决策部分暂停；必要事件保留，恢复后核对再处理，最终验收不被绕过 |
| 换 Leader 或机器崩溃 | 接手者只需项目/任务入口即可定位目标、授权、执行会话、证据和下一步；检查真实现场及不确定动作，Boss 无需重述上下文 |
| 防止虚报 | 植入“报告通过但日志失败”、过期候选或不完整评审，项目门禁与 Leader 核验能够拒绝交付，记录真实限制 |
| 进度、耗时与额度 | Boss 查询得到新鲜状态，Leader 已介入的阶段顺带汇报；预计延期或已知额度受限及时说明，取不到统计时不编造 |
| 通知与收尾 | 投递失败/重复/未消费、监控失联可见；旧确认不能删除新异常；只回收本任务资源，清理未完明确保留，不虚报完成 |
