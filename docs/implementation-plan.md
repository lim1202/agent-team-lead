# 首版 Skill 制作计划

## 目标与范围

首要体验是用户无需在工具间复制交接提示词和搬运汇报：由 Leader 直接完成派发、结果获取及返修交接。重点解决跨 Agent 工具委派，保持流程可复用，不替换原生子智能体调度。依据 [首版设计](v0-design.md)，先交付可独立阅读和本地加载的指令版 Skill。这一阶段仅制作仓库内的 Skill 包及文档，不启动真实执行任务或改动全局安装配置。

此交付实现协作指令，不等同于某条执行路径完成端到端验收。原生能力不足时如实披露，不增加未经验证的 CLI 适配、后台服务、自建审批器或模型路由。后续运行机制和具体工具路径另行验证。

- [x] 编写 Skill：开工简报、充分委派与两层授权、低成本跟进、真实性核验、唯一协调者接管、恢复及交付。

- [x] 走查首次开工、自动审批不可用、换 Leader、执行结果不明、证据失效等情景；区分指令覆盖与真实行为验证。
- [x] 更新公开状态、记录结果并提交本任务修改；不 push 或全局安装。

## 验证边界

格式校验和情景走查只能证明结构正确、规则可定位且未发现明显矛盾，不能证明某个模型实际遵循指令，也不能证明跨工具通知、自审批和恢复已跑通。真实执行验证需要具备相应权限和能力的目标宿主，不以旧实验结果替代。

## 验证结果

- skill-creator 官方 `quick_validate.py`：通过。验证环境独立放在系统临时目录，YAML 依赖不加入项目。
- UI 元数据、包内资源及公开文档链接、未完成脚手架标记、私人标识和差异检查：通过。
- 首次开工：核对已有开工确认，避免重复确认；未确认前不派发。
- 跨工具交接：指令要求 Leader 直接派发、取回原始结果及返修，不把复制粘贴交给用户；无法直接传递时在开工前披露。
- 自审批不可用：披露实际能力，不能将普通逐项审批转嫁为默认工作方式，也不将宽泛 Shell 放行伪称自动审查。
- 换 Leader：先接管协调责任和事件目标，旧协调者不再推进；无法确认时先对账。
- 执行结果不明：检查原进程及真实产物，未确认外部副作用之前不重试。
- 证据失效：检查候选与结果适用范围；报告标签和退出码不能直接通过验收。

上述情景为文档走查，不是通过独立模型或真实工具执行的行为测评。新 Skill 尚未验证任何完整跨工具路径，不沿用实验的 98 项测试作为新 Skill 的测试结果。

## 接续

当前阶段：指令版源码完成，已安装到 Antigravity 试点环境并通过文件一致性及格式检查，未发布；实际识别与跨工具闭环仍待试点验证。

### 下一阶段改进重点（未开始实现）

1. **缩短启动提示词。** 通用的派发、授权、跟进、验收和恢复约定由 Skill 承载，项目规则由 Harness 承载；用户只提供任务目标、页面/来源和本次例外。以简短任务描述能否引导 Leader 读取正确规范、提出开工简报并直接组织执行为验收方向，不依靠用户重复提醒固定约定。
2. **复用监测脚本。** 优先评估两项实验已有脚本，提取进程/活动采样、心跳、持久事件、去重、有限重试与处理确认；修正已观察到的未处理事件覆盖问题。通用监测与工具特定的状态读取、通知投递分开，只补实际能力缺口，避免 Leader 每次重新设计监控。核实源码复用许可，不默认引入后台服务或高频模型巡检。

后续验证重点：在实际宿主中跑通无需人工搬运消息的跨工具交付，核对执行端自审批、事件真实消费、失败保留与 Leader 交接。监测脚本须用隔离故障验证事件不丢失、重复通知不重复执行；Codex 的投递能力不直接视为 Antigravity 的已验证能力。现阶段仅确定改进方向，不声明上述能力已实现。
